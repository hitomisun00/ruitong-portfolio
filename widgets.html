Designing the control plane for portable product experiences.

Once a feature could travel into a broker site, every decision became a boundary: what follows the source, what an operator can change, and what the runtime must protect. I turned those decisions into a reusable widget system—and then a human-guided AI workflow for generating the next configuration.

The product problem

A portable feature cannot become a second source of truth.

The early widgets proved that an embed is not just a smaller screen. It introduces a new host, new dimensions, new branding needs and new runtime failure states—without permission to duplicate the feature’s business rules.

Without a model

Copied defaults look correct, then silently drift.

A widget can preserve an old title, status or display rule after the source feature changes. Operators cannot tell which value is still live.

With explicit authority

Every control says who owns the value.

Availability stays with the feature. Approved fields inherit until an override exists. Layout and appearance remain widget-only.

Decision one / source authority

Inheritance stays live until the operator makes a deliberate exception.

The resolution rule is small, but it prevents an entire class of drift: effective value = widget override ?? current feature value. Reset removes the override; it does not copy today’s feature value into a new snapshot.

Product judgement

Customization is useful when it communicates a valid state—not when it can manufacture one.

Decision two / configuration grammar

One predictable shell. Different controls for each feature.

The answer was not a universal form. It was a stable grammar that gives feature-specific choices a predictable home and keeps styling power inside safe boundaries.

Settings

What appears and how it behaves

  • Selection and ordering
  • Layout and display behavior
  • Sections, fields and nested content
  • Inherited values and explicit overrides
Style

How approved surfaces look

  • Theme and typography
  • Background and stroke
  • Radius, padding and gaps
  • Dividers across three surface depths
Setup

How the experience reaches its host

  • Widget mode and identifier
  • Domain access
  • Embed guidance
  • Runtime and provider requirements
Constrained by design

Useful freedom without raw CSS.

Operators can control the visual surfaces they actually need. Arbitrary positioning, dimensions, z-index, opacity, gradients and overflow stay out because they can break responsiveness, hierarchy or accessibility.

The Figma origin / Milestones

The first configurator was already a smart solution. Its depth revealed the next problem.

A one-size-fits-all widget could not satisfy different client brands, layouts and content needs. I designed a modular Milestones configuration model that could hide, show, arrange and style the parts of the experience without changing what the feature meant.

Original Figma design evidence. Scroll the rail and switch between Settings and Style.

Why it workedGranular enough for real client variation

Groups, stages, conditions, rewards, progress and brand surfaces could be composed instead of hard-coded.

What it exposedEvery feature needed a new control model

The system concepts repeated, but labels, relationships and safe exceptions changed from Store to Milestones to Streaks and Socials.

The turning pointGenerate the repeatable structure; review the feature-specific decisions

The workflow problem

I was still re-deciding the same system for every new widget.

The long Milestones rail made the pattern tangible. The feature-specific controls changed, but the questions repeated: which source is authoritative, which choices are safe, how they should be grouped, and which states need proof. I encoded that reusable judgement into a governed, resumable skill.

  1. RequestDescribe the feature and desired outcomeStart at discovery, implementation, QA or handoff
  2. InspectRead the feature and closest approved patternSeparate product questions from technical discovery
  3. ProposeGenerate a grouped control modelClassify authority, visibility, styling and states
  4. ReviewResolve feature-specific exceptionsA human confirms ambiguity, risk and source ownership
  5. DeliverImplement and prove the requested checkpointUse locked targets, proportional QA and evidence
The skill acceleratesRecurring structure

Canonical groups, common controls, authority labels, test scenarios and resumable run state.

What changed

The output was not one better editor. It was a way to keep product logic coherent as the platform grew.

The strongest idea proved to be the authority model: source capability, explicit overrides and widget-only presentation. The workflow then moved repetitive planning onto a proposal, leaving human attention for the feature-specific decisions where it mattered.
